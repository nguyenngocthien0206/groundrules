# SPEC: Groundrules

Repo name: `groundrules`. Tagline for the GitHub description and README header:
"Write down the rules your senior analyst never did, so your AI agent can follow them. Semantic models, decision records, and golden questions in CI, built on dbt."

The name is a deliberate double meaning: "ground rules" are the business rules everyone must follow, and "grounding" is how an AI agent is anchored to trusted definitions.

## 1. Goal
An open-source reference implementation that a real company can adopt on its existing dbt project and warehouse to make business definitions safe for AI agents.

A data lead should be able to:
1. Clone the repo and see the whole loop working locally in under 10 minutes, with no cloud account.
2. Recognize their own company in the example: messy sources, conflicting dashboards, rules nobody wrote down.
3. Copy the governance pieces (decision records, golden questions, CODEOWNERS, CI, playbook) into their own repo in an afternoon.
4. Point the same project at Snowflake, BigQuery, Databricks or Postgres by changing `profiles.yml`, the source definitions and the few staging models that depend on how data lands (`adoption/warehouses.md`); marts and the semantic layer stay as they are.

Companion to the Substack article "When the One Asking for Data Is No Longer a Person" (link placeholder: `SUBSTACK_URL`).

## 2. Non-goals
- Not a new semantic engine or standard. Use dbt + MetricFlow for definitions; export or map to Open Semantic Interchange (OSI) where supported.
- Not a hosted product, no web UI. The optional Power BI report (section 13) is a file opened in a tool the company already owns.
- No LLM calls in the core demo or default CI. Agent pieces are optional phases.

## 3. Phases
| Phase | Scope | Why it matters to an adopting company |
| --- | --- | --- |
| v0.1 Core | Realistic data, dbt project, semantic models, decision records, golden questions, governance CI, drift and conflict demos, optional Power BI dashboard on certified exports, playbook | Works with no AI at all. Pays off for dashboards on day one. |
| v0.2 Agent-ready | MCP access to the semantic layer (built on `dbt-mcp` where possible), agent eval harness on golden questions | Shows how an agent should consume certified definitions and how to measure it. |
| v0.3 Actions | One action contract, shadow table, simulation, approval, idempotent write-back, audit log | Shows the safe path from answers to actions. |

Build v0.1 completely before starting v0.2. Ask me before starting v0.2 or v0.3.

## 5. Synthetic data that looks real (`example/generate.py`)
A fictional pharmacy retail chain in Vietnam ("Northwind Pharmacy" style invented name, never a real brand). Fixed seed. Fixed snapshot date 2026-09-15. Output as raw extracts, the way they arrive from source systems, not as clean tables.

Sources:
| Source system | Extract | Realistic problems to include |
| --- | --- | --- |
| ERP | stores | `opened_on` date; two stores opened in the last month |
| ERP | skus | SKU renamed mid-period; VAT rate per SKU; base unit and pack sizes (box, strip, tablet) |
| ERP | batches | `unit_cost` per batch; `received_qty` and `received_at` in boxes; expiry date |
| ERP | transfers | status codes instead of words (`TR`, `DL`, `CX`); a cancelled transfer still present; quantities in boxes |
| POS (two vendors) | sales lines | different column names and date formats per vendor; vendor A stamps UTC, vendor B stamps local time; duplicate lines from a retry; amounts in VND as integers, VAT included; `discount_amount` per line; sold in strips or tablets |
| POS sync log | last sync per store | two newly opened stores lagging 3 days behind |
| Returns system | returns | returns arriving weeks after the sale; some returns with no matching sale |
| Logistics provider | store routes (v0.3) | road km and drive minutes per direction between stores, over an invented city with a river and two bridges, so district lines and travel time disagree; metres, seconds and UTC timestamps; pairs re-sent with an update; no routes yet for stores opened in the last month |

Scale: about 30 stores in 5 districts, 150 SKUs across 6 categories, 6 months of sales. Small enough for DuckDB on a laptop, large enough that wrong rules produce visibly wrong numbers.

The data must make every tacit rule matter: batches under 90 days to expiry, outbound transfers in transit, cancelled transfers, late returns, duplicate POS lines, lagging stores, VAT in POS prices, mixed units of measure, and sales near midnight that land on a different business day in UTC.

VAT rates and pack sizes are set in the generator and are illustrative only. They are not tax advice and not any real chain's master data.

Reproducibility: golden expected values are frozen from this output, so the generator must produce byte-identical files on every machine. Pin every library version, and keep a checksum test in `tests/` that fails if the output changes.

## 6. dbt project (`dbt/`)
- Staging: one model per source, rename to a common vocabulary, decode status codes, dedupe POS retries, convert types, convert POS timestamps to local business time (Asia/Ho_Chi_Minh), convert quantities to the SKU base unit, split VAT out of POS amounts. Document every column.
- Intermediate: `int_sales_lines` (both vendors in one shape, base units, amounts with and without VAT), `int_return_lines` (base units, before VAT, original sale date when the receipt is found) and `int_store_sku_costs` (weighted average cost per store and SKU, DR-008).
- Marts: `dim_store` (with `opened_on`, `is_newly_opened`, `last_synced_at`, `pos_lag_days`, `is_pos_sync_lagging`), `dim_sku`, `fct_inventory_batch`, `fct_transfers` (with `snapshot_date`), `fct_sales` (with `unit_cost_excl_vat` and `cogs_excl_vat`), `fct_returns`, `fct_goods_received` (stock received from suppliers or by transfer; not "receipts", which already means sales receipts here), and `metricflow_time_spine`.
- The properties of each mart (contract, docs, tests, semantic model) live in `models/semantic/<mart>.yml`, next to its metrics (section 7).
- Marts expose neutral facts, never business thresholds. For example `fct_inventory_batch.days_to_expiry` (computed against the snapshot date), `fct_transfers.transfer_status`, `fct_returns.return_date`. The 90-day rule, the cancelled-transfer exclusion and the return-month rule live in the semantic layer (section 7), so changing them always touches a file that CODEOWNERS protects.
- Marts that feed a certified metric use `contract: enforced` and `access: public`. A column rename then fails the build instead of silently breaking a metric.
- Unit tests (dbt `unit_tests`) for the logic most likely to break quietly: POS retry dedupe, status code decoding, UTC to local business day, unit of measure conversion, VAT split.
- Data tests (generic and singular): uniqueness, not null, accepted values.
- Freshness: `dbt source freshness` with `loaded_at_field` on the POS sources, plus a singular test that flags each store whose POS sync lags.
- Data tests check the data is clean. Golden questions check the meaning is right. Keep both and explain the difference in README.
- `profiles.example.yml` with commented blocks for duckdb, snowflake, bigquery, databricks, postgres.

## 7. Semantic layer (`dbt/models/semantic/`)
Use MetricFlow semantic models and metrics in dbt's latest YAML spec: the semantic model sits on the model (`semantic_model: {enabled: true}`, `agg_time_dimension`), entities and dimensions sit on columns, and simple metrics with direct keys (`agg`, `expr`, `filter`, `non_additive_dimension`) replace measures. Verified on dbt-core 1.12.6 with dbt-metricflow 0.15.0 (MetricFlow 0.213.0) on DuckDB: `mf validate-configs`, `mf query`, saved queries and the Python engine all work. Quirks found and handled are listed in PROGRESS.

Layout: in this spec a semantic model must sit in the same properties file as its model, so each mart's properties live in `models/semantic/<mart>.yml`, together with the simple metrics built on it. Metrics that combine several semantic models live in one file per owning team (`models/semantic/metrics_finance.yml`, `metrics_supply_chain.yml`). Every business rule therefore sits in this folder.

Building-block metrics (for example on-hand units, sales before VAT) are `hidden: true`. They feed the certified metrics but do not show in `mf list metrics`, in the OSI document, or to agents.

Use what dbt already provides before adding custom fields:
- Business owner: the metric's dbt `group` (defined in `models/groups.yml`, a team handle, never a person's name).
- Data owner: the `group` of the mart behind the semantic model, usually `data_platform`.
- Description and label: the native `description` and `label`.

Only what dbt has no field for goes into `meta`:
```yaml
config:
  group: supply_chain_ops
  meta:
    version: 3
    status: certified            # draft | certified | deprecated
    certified_on: 2026-09-10
    recertify_every_days: 180
    decision: decisions/DR-001.md
    replaced_by: null            # required when status is deprecated
    agent_notes: "Use this, never sum qty_on_hand directly."
```

Business thresholds and exclusions are written as metric or measure filters here, not in mart SQL. For example the 90-day rule is a filter on `days_to_expiry` inside `available_stock`.

Metrics for v0.1:
| Metric | Rule written down |
| --- | --- |
| `available_stock` | on hand in base units in batches with at least 90 days to expiry, minus outbound transfers in transit (cancelled ones not subtracted). Semi-additive over time: `non_additive_dimension` on the snapshot date |
| `near_expiry_value` | cost value of stock in batches with fewer than 90 days to expiry, expired stock not yet written off included |
| `net_revenue` | sales after discounts and before VAT by sale date, minus refunds before VAT by return date |
| `gross_margin` | net revenue minus cost of goods sold at the store's weighted average cost for the SKU; not reversed for returns (destroyed) |
| `sell_through_rate` | base units sold (gross of returns) over base units received net: from suppliers and other stores, minus transfers out; no value when net received is zero or negative, and a `new_store` caveat for stores opened in or just after the period (DR-011) |
| `days_of_cover` | available stock at the snapshot over average daily base units sold in the 28 full days before it (a 28-day cumulative window offset by one day) |

Also include one `deprecated` metric, `revenue_v1` (VAT included, by sale date, returns ignored), with `replaced_by: net_revenue`, to show the lifecycle.

Saved queries: the slices the dashboard shows (section 13) are defined as dbt `saved_queries` in this folder. They are the only way a dashboard gets a number.

OSI: dbt 1.12 writes an Open Semantic Interchange document (`target/osi_document.json`, OSI 0.1.1) on every parse, with hidden metrics left out. `make export-osi` runs the parse and points to it.

## 8. Legacy conflict (`legacy/`)
Three SQL files that mimic real dashboards: `finance_dashboard.sql`, `sales_dashboard.sql`, `ops_weekly_report.sql`. They read the marts, the way an old dashboard reads the warehouse, and each differs from `net_revenue` by exactly one rule that has a decision record: refunds put back on the month of the sale (DR-002), returns left out (DR-002), till amounts with VAT included (DR-006). `make demo-conflict` (`demos/conflict.py`, optional `MONTH=YYYY-MM`) runs all three plus the certified metric for the same month and prints the four numbers side by side with each gap and its reason, then the DR that settled it (who decided, when, after hearing whom) and the golden question that guards the number. It exits 1 if two answers agree, so the demo cannot silently stop making its point. Each legacy dashboard is declared as a dbt `exposure` with an owner and `maturity: low`, the way a company would catalog what it already has.

## 9. Decision records (`decisions/`)
Format (MADR style): YAML front matter for what the lint reads (`id`, `title`, `status` proposed | accepted | superseded, `date`, `decided_by` role, `consulted` roles, `linked_metrics`, `linked_golden_questions`, `supersedes`, `superseded_by`), and body sections for people: Context, Decision, Options considered, Consequences, Worked example (one real case from the data, computed by hand and cross-checked once against MetricFlow). `TEMPLATE.md` and an index in `README.md`. A record is never edited to change its decision; a new record supersedes it.

v0.1 records:
- DR-001: available stock excludes batches under 90 days to expiry (60 vs 90 considered).
- DR-002: net revenue counts returns in the month of the return (finance vs sales; who broke the tie and why).
- DR-003: cancelled transfers are excluded from in-transit stock.
- DR-004: POS data rules. The business day is local time (Asia/Ho_Chi_Minh), whatever timestamp the vendor sends. Stores lagging POS sync are included but flagged; answers must carry a caveat.
- DR-005: deprecate `revenue_v1` in favor of `net_revenue`.
- DR-006: revenue metrics are reported before VAT (finance and tax view vs the shelf price store managers see).
- DR-007: stock and sell-through are counted in the SKU base unit; boxes and strips are converted, never added as they are.
- DR-008: cost of goods sold uses the weighted average cost per store and SKU over all its receipts, because POS lines carry no batch (store-level vs chain-level average considered). Returns are destroyed, so their cost is not reversed.
- DR-009: sell-through divides gross units sold by units received net (suppliers plus transfers in, minus transfers out), so it is right per store and for the chain (supplier-only and supplier-plus-transfers-in considered).
- DR-010: days of cover uses the pace of the 28 full days before the snapshot day (7, 90 and a window ending on the snapshot day considered).
- DR-011 (supersedes DR-009, added after v0.1's first dashboard export): sell-through keeps DR-009's formula, has no value when net received is zero or negative, and flags a store that opened after the period began and within 7 days after it ended (opening stock arrives in the week before opening). Hiding new stores on the dashboard only, leaving out opening stock, and clamping at zero were considered.

DR-001 also records that near-expiry value includes expired stock not yet written off.

## 10. Golden questions (`golden/`)
About 30 questions, grouped by domain, covering four kinds:
| Kind | Example | What it protects |
| --- | --- | --- |
| Tacit rule | Available stock of an item in one district | the 90-day, in-transit, base unit and VAT rules |
| Conflict | Net revenue for August | the certified definition beats legacy ones |
| Caveat required | Sales yesterday across all stores | answer must flag lagging stores and use the local business day |
| Deprecated | Revenue using `revenue_v1` | must point to the replacement |

Fields in `golden/questions/*.yml` (written and signed off by people): `id`, `question`, `kind` (tacit_rule | conflict | caveat_required | deprecated), `metric`, `filters` (`store`, `sku`, `district`, `category`, and one of `day`, `month`, or `start` + `end`), `as_of`, `tolerance` (absolute, in the metric's unit), `why`, `decision`, `signed_off_by` (role), `signed_off_on`, plus `expected_replacement` for deprecated questions. `expected` and `expected_caveats` (for example `pos_sync_lag:NW029`) live in the generated `golden/expected/<domain>.yml`, so a script never rewrites what people wrote and each domain owner reviews their own numbers.

Expected values come from `golden/reference/`: SQL over the raw extracts, one file per metric, each citing the decision records it implements. SQL because that is what teams use for reconciliation in practice: analysts and owners can read and sign it, and an adopter swaps `read_csv(...)` for their raw tables. It never reads the marts, dbt or MetricFlow; a test enforces this. Money is summed as decimals so every run gives the same digits. `make golden-freeze` writes `golden/expected/` with the data fingerprint; a test fails if it differs from a fresh reference run.

How to keep the reference really independent: write each reference computation from the text of its DR, before the matching metric exists. Each DR's worked example must also appear in `why` of at least one golden question, so a person can check one number without running anything.

How each kind passes in v0.1 (there is no agent yet, so the runner plays that role):
- Tacit rule and conflict: the semantic layer value is within `tolerance` of `expected`.
- Caveats, on every question: the runner derives them from data (DR-004, stores and days). A store in scope whose POS data ends before the day before `as_of` adds `pos_sync_lag:<store>` when the period reaches past its last day of data, or when the metric is a stock position at `as_of`. For sell-through (DR-011), a store in scope that opened after the period began and no more than 7 days after it ended adds `new_store:<store>`. A question passes only when the value matches and the derived caveats equal `expected_caveats` exactly, so a missing caveat and an unneeded one both fail.
- Deprecated: the runner refuses to return the old metric's number. It passes when the metric has `status: deprecated`, `replaced_by` points to a certified metric, and the runner's answer names that replacement.

`run_golden.py` queries the semantic layer through MetricFlow's Python API (not one `mf query` subprocess per question, which reloads the project each time), compares with tolerance, checks caveats, prints a table, shows `why` and the DR link on failure, writes a JUnit XML report for CI, and exits non-zero on failure. Measure its run time and keep the whole quickstart under 10 minutes. (28 questions run in about 10 seconds.)

## 11. Governance in Git
- Ownership has one source: the dbt groups in `models/groups.yml`, each with `config.meta.github_team` (placeholder handles such as `@your-org/supply-chain-ops`). Groups: `supply_chain_ops`, `finance`, `retail_operations`, `data_platform`.
- `CODEOWNERS`: on GitHub the last matching line wins, and when a line lists several teams, any one of them can approve. So a file holding a team's rules is owned by that team alone: cross-model metrics are split by owner (`metrics_finance.yml`, `metrics_supply_chain.yml`), and expected values by domain (`golden/expected/<domain>.yml`, mirroring `golden/questions/`). Decision records and golden files are owned by every team whose metrics they cover; mart SQL by the data platform plus the teams that rely on it. "Require review from Code Owners" must be on in branch protection; where all teams must approve, use a ruleset.
- `pull_request_template.md`: what changes and why, metrics, decision record (new or superseding), golden questions, affected metrics and exposures (`make affected`), and a checklist (lint and tests, re-freeze reviewed, registry regenerated, version bumped, owners approved, exposure owners told).
- `governance/lint.py` runs on `target/manifest.json` (after `dbt parse`), not on hand-parsed YAML. Each check takes loaded data (`governance/repo.py`), so tests feed it broken copies. It fails when:
  - a visible metric has no `group`, lacks a governance field, or has an unknown status; a group has no `github_team` (hidden building blocks are exempt);
  - a decision link is broken, a decision record does not list its metric, misses front matter keys or sections, or is not in `decisions/README.md`;
  - a certified metric has no golden question, a question and its decision record do not point to each other, a reserved question id does not exist, or `golden/expected/` does not mirror `golden/questions/`;
  - a deprecated metric has no `replaced_by`, or it points to a metric that is not certified;
  - a model behind a semantic model has no enforced contract;
  - CODEOWNERS disagrees with the groups: a file holding rules must be owned by exactly the teams of the metrics those rules shape (a hidden building block counts for the certified metrics that use it); decision records and golden files must reach every team they cover;
  - any text file Git sees contains the em dash character (U+2014);
  - `governance/registry.md` is out of date;
  - a Power BI measure recomputes a metric (section 13, step 8);
  - a governed metric's current version has no entry in `CHANGELOG.md`.
- Staleness: a certification older than `recertify_every_days` is a warning, `--fail-on-stale` makes it an error. Lint takes `--today`. The default is the snapshot date (2026-09-15), so the demo gives the same result on any calendar day. A company's real CI passes the actual date (`make lint LINT_ARGS="--today ..."`).
- Recertification follows the business review rhythm: 90 days for finance metrics (quarterly review), 180 days for operations metrics.
- `governance/affected.py` (`make affected BASE=origin/main`) lists the governed metrics and exposures a branch touches, following dbt lineage from the changed files, ready to paste into the PR template.
- `governance/registry.md` (`make registry`): generated tables of every governed metric (label, owner and team, version, status, certified on, recertify by, decision record, number of golden questions, replaced by) and of the exposures that read the data. It shows the due date rather than "stale", so the file does not change with the calendar. The lint fails when it is out of date, and CI also runs `git diff --exit-code`.
- CI (`.github/workflows/governance.yml`, GitHub Actions on Ubuntu): on every pull request and push to main, one step per promise, calling the same `make` targets as people do locally: locked install, data, build, lint with the real date, `make registry` plus `git diff --exit-code`, golden questions (JUnit report kept as an artifact), dashboard export, pytest, both demos (and no file changed afterwards), `make check-v2`; on pull requests, `make affected` into the job summary. A weekly scheduled run adds `--fail-on-stale`. Actions are pinned by commit SHA. Branch protection makes `governance` a required check together with "Require review from Code Owners".
- `CHANGELOG.md`, kept by hand, in two parts: **Definitions** for the people who read the numbers (each change of a certified number's meaning: what changed, what moves, decision record, golden questions, pull request) and **Repository** in Keep a Changelog style. The lint fails when a governed metric's current version has no Definitions entry.

## 13. Dashboards (Power BI, optional)
Most companies already own a BI tool, and the biggest risk is that the tool quietly becomes a second place where metrics are defined. This section shows the safe pattern with Power BI Desktop. It is optional: an adopter can delete `dashboards/` and keep everything else, and its definition-of-done item is checked separately from the core ones. In this repo `make test` runs the export first, so the dashboard tests always have fresh data.

Why not connect Power BI straight to the semantic layer: dbt's official Power BI connector needs the dbt platform (Starter plan or above) and is in preview. Open-source MetricFlow on DuckDB has no server for it to talk to, and Power BI has no native DuckDB connector. So the repo copies what companies on the dbt platform do with saved queries and exports.

How it works:
1. Every slice the report shows is a dbt saved query (section 7), in one file per owning team: `saved_queries_finance.yml` (net revenue and gross margin by month, by district and month, by category and month) and `saved_queries_supply_chain.yml` (sell-through by store and month; available stock, near-expiry value and days of cover by store and by category at the snapshot). A saved query decides which slice of a metric managers see, so the lint requires its file to be owned by the teams of the metrics it exports. Monthly slices start at the first full month of POS data (April 2026): before it the ERP has receipts but the tills have no sales, so a ratio would read 0 where the truth is "no data", and a half month would read as a bad month.
2. `make dashboard-data` runs `dashboards/export.py`, which executes each saved query through MetricFlow and writes one Parquet file per saved query to `dashboards/exports/` (not committed), with readable column names plus `as_of` and `caveats` (the same caveat strings and rules as the golden runner, for example `new_store:NW030, pos_sync_lag:NW030`). A ratio with no value stays empty, never 0. Monthly rows also carry `data_through` and `is_month_to_date`, so the current month reads as month to date, and the export refuses a month that starts before the POS history. It also writes `metric_versions.parquet` (metric, version, status, owner, decision record) for the report's footer, and refuses to export a metric that is not certified.
3. `dashboards/groundrules.pbip` is a Power BI project: the semantic model in TMDL and the report in PBIR, both text, so changes are reviewed in a PR like any other definition. It imports the Parquet files with Power BI's built-in Parquet connector, so nothing needs to be installed. Power BI has no relative paths, so the `ExportFolder` parameter is set once after cloning. Every PBIR file was checked against Microsoft's published JSON schemas, and the committed files are as Power BI Desktop saves them. A save in Desktop also writes the saver's own folder into `ExportFolder`, can turn on Auto date/time, and resets columns to `sum` unless they carry `SummarizationSetBy = User`; the lint fails on each of these, so a careless save never reaches main.
4. The report never recomputes a certified metric. Ratio and semi-additive metrics (`sell_through_rate`, `days_of_cover`, `available_stock`) are exported at exactly the grain the visual shows, because summing them again in DAX gives a wrong number. Each measure is `SELECTEDVALUE` over one exported column, metric columns are hidden with `summarizeBy: none`, and the model sets `discourageImplicitMeasures`. Totals stay blank on purpose: a total that was not exported is not certified. Lint reads the TMDL files and fails when a measure uses anything beyond display functions (`SELECTEDVALUE`, `MAX`, `MIN`), has no `///` description naming a certified metric and its current version (for example `metric: net_revenue v2`), or when a metric column can be summed.
5. A pytest compares the exported Parquet with golden expected values, caveats included, wherever a saved query and a golden question cover the same slice. The numbers on the dashboard are then backed by the same proof as the metric. Another test checks that every visual asks only for tables, columns and measures that exist in the TMDL.
6. The report is declared as a dbt `exposure` (`groundrules_powerbi_report`) that depends on the six certified metrics, so `make affected` lists it when a metric changes.

Limits, stated plainly in README: Power BI Desktop runs only on Windows, so CI runs the export, the TMDL lint and the pytest, and opening the report is a manual step. Mac and Linux users can point any BI tool at the Parquet files. A company on the dbt platform replaces step 2 with dbt exports or the official connector, and keeps everything else.

## 14. Playbook (`playbook/`)
- `running-a-definition-session.md`: attendees, prep, how to break ties, the three outputs of every session (DR, metric change, golden questions).
- `ownership.md`: business owner vs data owner, what each is accountable for, how they map to dbt groups, and a RACI table template.

## 17. v0.2 Agent-ready (do not start without asking)
- MCP access: build on the official `dbt-mcp` server first, in line with "build on what companies already run". Verified in step 12: its semantic layer tools need the dbt platform (`DBT_HOST`, `DBT_TOKEN`, `DBT_PROD_ENV_ID`) and it needs Python 3.12 or later, so locally it would only give an agent dbt CLI tools. The repo therefore has a thin server, `mcp_server/semantic.py` (named so it cannot shadow the `mcp` SDK package): `list_metrics`, `describe_metric` (definition, owner, `agent_notes`, decision record, caveats), `find_values` (names to codes) and `query_metric`, which reuses the golden runner's code path. Deprecated and draft metrics are refused with a pointer to the certified one; no value stays null. `mcp_server/raw_sql.py` is the agent eval's control arm: read-only SQL over the marts. MetricFlow readers open the warehouse read-only so several servers can share it.
- `agent_eval/`: runs the golden questions through an agent connected over MCP to one arm (`semantic` or `raw_sql`), and grades each answer with `run_golden.check()`: correct (number and caveats), right number, right caveats, per question kind. Results per (question, rep) in `agent_eval/runs/<run-id>/<arm>/` (results, traces, errors; resumable); `summary.py` reports means over questions with bootstrap intervals. Providers: `claude-code` (Claude Code 2.1.221+ headless on a subscription; clean context from an empty folder with CLAUDE.md, auto memory and bundled skills off, checked by a probe) and `anthropic-api` (the Claude API with a key; written, not yet run). Not in CI; its grading, runner and stream parser are tested in CI without a model. Measured in step 14 (Sonnet 5.5, Claude Code 2.1.311, 30 questions x 3 reps x 2 arms, 180 answers, no errors; evidence in `agent_eval/results/v0.2.0/`): governed 99% correct (97% to 100%), raw SQL 8% (0% to 18%), right number 99% versus 13%.

## 20. Definition of done (v0.1)
- On a fresh clone: `make setup && make data && make build && make test` passes in under 10 minutes on a laptop.
- The generator checksum test passes on a second machine.
- `make demo-conflict` prints four different net revenue numbers and names the DR that settled it.
- `make demo-drift` shows golden questions failing for the right reason, then restores everything.
- `make lint` fails with a clear message when an owner group is removed, a DR link breaks, a certified metric has no golden question, a deprecated metric has no replacement, or an em dash appears.
- `make lint` gives the same result on any calendar day with the default `--today`.
- CI fails when `registry.md` is out of date.
- Optional dashboard, checked separately from the core items: `make dashboard-data` writes Parquet that matches golden expected values, and the Power BI report opens and refreshes on Windows (manual check).
- Switching to another warehouse is documented in `adoption/warehouses.md`: profiles, source definitions, the staging models that depend on how data lands, and the reference's raw views change; marts and the semantic layer do not (documented, not tested in CI).
- No real company names or rules, and no em dash character anywhere in the repo.
